#### ข้อที่ 2: Normalization (10 คะแนน)
**สถานการณ์:** 
ฐานข้อมูลโครงการและพนักงานของบริษัทถูกจัดเก็บในตารางเดียว (Single Table) ที่มีชื่อว่า `EMP_PROJ_DEPT` เพื่อความง่ายในการดูข้อมูล ดังโครงสร้างต่อไปนี้:

**EMP_PROJ_DEPT** (<u>EmpID</u>, <u>ProjID</u>, HoursWorked, EmpName, DeptID, DeptName)
*หมายเหตุ: Primary Key หลักของตารางนี้คือ Composite Key `{EmpID, ProjID}`*

**Functional Dependencies (FDs) ที่ถูกระบุไว้:**
*   **FD1:** `{EmpID, ProjID} -> HoursWorked` *(รหัสพนักงาน+รหัสโปรเจกต์ ระบุชั่วโมงทำงานได้)*
*   **FD2:** `EmpID -> {EmpName, DeptID}` *(รหัสพนักงานเดี่ยวๆ ระบุชื่อและแผนกของพนักงานได้)*
*   **FD3:** `DeptID -> DeptName` *(รหัสแผนก ระบุชื่อแผนกได้)*

5. **ข.** (Predicate Pushdown คือดันเงื่อนไขกรองบรรทัด $ \sigma $ ไปทำก่อนการ $ \bowtie $)
6. **ข.** (การหั่นแบ่ง "แถว (Row)" ตามเงื่อนไข เรียกว่า Horizontal Partitioning)
7. **ก.** (Index ทำให้ SELECT เร็วขึ้น แต่มีผลให้ DML ช้าลงและกิน Storage)
8. **ง.** ( $ A \times A $ หรือ Cartesian Product ของ 100 แถว จะได้ $ 100 \times 100 = 10,000 $ แถว ซึ่งมากที่สุดเสมอ)
9. **ข.** (EXISTS เช็คว่ามีผลลัพธ์ส่งกลับมาจาก Subquery หรือไม่)
10. **ข.** (เพิ่มปริมาณข้อมูลที่โอนถ่าย Data transfers และตัดโอกาสในการทำ Projection Pushdown)
11. **ก.** (ลบข้อมูลลูก ดันพาลลบข้อมูลแม่หายไปด้วย)
12. **ข.** (WHERE กรองก่อนจัดกลุ่มเลยเร็วกว่า, HAVING กรองหลังจัดกลุ่ม)
13. **ค.** (ตามหลัก 3VL ค่า `TRUE AND UNKNOWN` จะได้ `UNKNOWN`)
14. **ข.** (NULL ไม่ใช่ค่า 0 หรือค่าว่างเปล่า แต่แปลว่าไม่ทราบค่า จึงหาความเท่ากันด้วย `=` ไม่ได้)
15. **ค.** (อุดช่องโหว่ 3NF ที่บางทีตัวกำหนดไม่ใช่ Candidate key)
16. **ก.** (Atomicity = All or Nothing)
17. **ข.** (View ซ่อนข้อมูลละเอียดอ่อน เช่น เงินเดือน และทำคิวรีซับซ้อนให้ใช้ง่ายขึ้น)
18. **ข.** (`UNION` เฉยๆ จะตัดตัวซ้ำทิ้ง, `UNION ALL` จะเก็บตัวซ้ำไว้)
19. **ค.** (`> ALL`)
20. **ค.** (DRC อ้างอิงตัวแปรเป็นรายคอลัมน์ (Domain) ส่วน TRC อ้างเป็นรายแถว (Tuple))

**Part 2: Short Answer**
1. ยอมรวมตารางเพื่อลดการ JOIN ให้ Query เร็วขึ้น ผลเสียคือเกิด Redundancy (ข้อมูลซ้ำซ้อน) เสี่ยงต่อ Anomaly
2. Natural Key ใช้ข้อมูลจริงในโลก (เช่น เลขบัตร ปชช.), Surrogate Key คือคีย์เทียมที่ระบบรันให้ (เช่น ID 1, 2, 3) ไม่มีค่าทางธุรกิจ
3. Non-key attribute ไปเป็นตัวกำหนดค่าให้ Non-key attribute ตัวอื่น ละเมิดระดับ 3NF
4. $ \forall $ = ต้องเป็นจริงกับ "ทุกตัว" ในเซต, $ \exists $ = มี "อย่างน้อย 1 ตัว" ที่เป็นจริง
5. `IN` เทียบค่ากับกลุ่มผลลัพธ์ที่ได้มาจาก Subquery, `EXISTS` จะรีเทิร์นแค่ TRUE/FALSE ว่า Subquery นั้นมีข้อมูลโผล่มาหรือไม่
6. ข้อมูลไม่หาย เพราะคุณสมบัติ Durability ยืนยันว่าหาก Commit แล้วข้อมูลจะต้องถูกเขียนลง Disk อย่างถาวร
7. Procedural (เช่น RA) ต้องเขียนสเต็ปวิธีการดึงข้อมูลทีละขั้น, Non-procedural (เช่น SQL/TRC) แค่สั่งว่า "อยากได้ข้อมูลอะไร" ให้ระบบไปหาวิธีดึงเอง
8. CHECK กำหนดเงื่อนไขได้แค่ในตารางนั้นๆ แต่ ASSERTION สามารถสร้างเงื่อนไขเช็ค "ข้ามตาราง (Cross-table)" ได้
9. ใช้ดู Execution Plan ของ Database เพื่อประเมิน Cost และดูว่าคิวรีนั้นสแกนทุกบรรทัด (Table scan) หรือใช้ Index
10. ใช้ Double Negation โดยเขียน `NOT EXISTS` ซ้อน `NOT EXISTS` หรือ `NOT EXISTS (... EXCEPT ...)`

**Part 3: Long Questions**
**ข้อ 1 (Complex Query):**
1.1 **RA:** $ \pi_{Pname}(PROJECT) - \pi_{Pname}(PROJECT \bowtie_{Pnumber=Pno} WORKS\_ON) $
1.2 **TRC:** $ \{ p.Pname \mid p \in PROJECT \land \neg \exists w \in WORKS\_ON (w.Pno = p.Pnumber) \} $
1.3 **DRC:** $ \{ PN \mid \exists Pnum, Ploc, Dnum (PROJECT(Pnum, PN, Ploc, Dnum) \land \neg \exists Essn, H (WORKS\_ON(Essn, Pnum, H))) \} $
1.4 **SQL:**
```sql
SELECT Pname 
FROM PROJECT 
WHERE Pnumber NOT IN (SELECT Pno FROM WORKS_ON);
```

**ข้อ 2 (Normalization):**
2.1 **ตอบ:** ปัจจุบันอยู่ใน **1NF** (เพราะถือว่าข้อมูลในช่องเป็น Atomic หมดแล้ว) แต่ยังไม่เป็น 2NF เพราะ **ละเมิดกฎ Partial Dependency** จาก FD2 เนื่องจากกลุ่มแอตทริบิวต์ `EmpName, DeptID` พึ่งพาแค่ส่วนเดียวของคีย์หลักนั่นคือ `EmpID` เท่านั้น (ไม่ได้ขึ้นอยู่กับ ProjID)
2.2 **ทำให้เป็น 2NF:** (ฉีกคอลัมน์ที่มีปัญหา Partial Dependency ออกไป)
*   **EMP_PROJ** (<u>EmpID</u> (FK), <u>ProjID</u> (FK), HoursWorked)
*   **EMPLOYEE_INFO** (<u>EmpID</u>, EmpName, DeptID, DeptName)
2.3 **ทำให้เป็น 3NF:** (ฉีกคอลัมน์ที่มีปัญหา Transitive Dependency `DeptID -> DeptName` ในตาราง EMPLOYEE_INFO ออกไป)
*   **EMP_PROJ** (<u>EmpID</u> (FK), <u>ProjID</u> (FK), HoursWorked)
*   **EMPLOYEE** (<u>EmpID</u>, EmpName, DeptID (FK))
*   **DEPARTMENT** (<u>DeptID</u>, DeptName)
