# รายงานปฏิบัติการที่ 10: ธุรกรรม, ผู้ใช้, สิทธิ์, วิว, การทำดัชนี และการวิเคราะห์คิวรี่

## ส่วนที่ 1: ขั้นตอนและภาพประกอบ (Step-by-Step Screenshots)

### 1. คำสั่งจัดการ Transaction (Transaction Commands)

**คำแนะนำ:**
1.  รันชุดคำสั่ง SQL ในหัวข้อ **2.1 Demonstrate ROLLBACK**
2.  แคปภาพหน้าจอแสดงคำสั่ง `INSERT`, ผลลัพธ์ `SELECT` *ก่อน* rollback (เห็นข้อมูล), และผลลัพธ์ `SELECT` *หลัง* rollback (ข้อมูลหายไป)
3.  รันชุดคำสั่ง SQL ในหัวข้อ **2.2 Demonstrate COMMIT**
4.  แคปภาพหน้าจอแสดงคำสั่ง `INSERT`, คำสั่ง `COMMIT`, และผลลัพธ์ `SELECT` (เห็นข้อมูลยังอยู่)

**[ใส่ภาพประกอบที่นี่]**

**สรุปผลการทดลอง (Reflection):**
ในขั้นตอนการจัดการธุรกรรม (Transaction) ข้าพเจ้าได้ทดลองใช้คำสั่ง `BEGIN`, `COMMIT`, และ `ROLLBACK` โดยสังเกตเห็นว่าเมื่อใช้คำสั่ง `ROLLBACK` โปรแกรมจะยกเลิกการเปลี่ยนแปลงทั้งหมดที่เกิดขึ้นใน Transaction นั้น (เช่น การ INSERT ข้อมูล) ทำให้ข้อมูลไม่ถูกบันทึกลงในฐานข้อมูล ซึ่งแสดงให้เห็นถึงคุณสมบัติ Atomicity (ความเป็นหน่วยเดียวกัน) คือต้องสำเร็จทั้งหมดหรือล้มเหลวทั้งหมด ในทางกลับกัน เมื่อใช้คำสั่ง `COMMIT` การเปลี่ยนแปลงจะถูกบันทึกอย่างถาวร (Durability) ความท้าทายในส่วนนี้คือต้องไม่ลืมที่จะเริ่ม Transaction ด้วยคำสั่ง `BEGIN` เสมอ มิฉะนั้น PostgreSQL จะทำงานในโหมด Auto-commit โดยอัตโนมัติ

### 2. การจัดการผู้ใช้และสิทธิ์ (User and Privilege Management)

**คำแนะนำ:**
1.  รันคำสั่ง SQL เพื่อสร้าง `hr_user` และกำหนดสิทธิ์ (Grant)
2.  ตัดการเชื่อมต่อ หรือเปิดหน้าต่าง Terminal ใหม่ แล้วเชื่อมต่อฐานข้อมูลด้วยชื่อผู้ใช้ `hr_user` (เช่นใช้คำสั่ง `psql -U hr_user -d company_db`)
3.  ลองรันคำสั่ง `SELECT * FROM employee;` (แคปภาพตอนทำงานได้สำเร็จ)
4.  ลองรันคำสั่ง `DELETE FROM employee;` (แคปภาพตอนขึ้น Error ว่า Permission denied)

**[ใส่ภาพประกอบที่นี่]**

**สรุปผลการทดลอง (Reflection):**
ข้าพเจ้าได้สร้างผู้ใช้ใหม่ชื่อ `hr_user` และกำหนดสิทธิ์เฉพาะที่จำเป็น (เช่น `SELECT`, `INSERT`) บนตาราง `employee` โดยใช้คำสั่ง `GRANT` จากการทดสอบพบว่าผู้ใช้ใหม่สามารถดูข้อมูลได้ตามปกติ แต่เมื่อพยายามลบข้อมูลด้วยคำสั่ง `DELETE` ระบบจะไม่อนุญาตและแจ้งเตือนสิทธิ์การเข้าถึง สิ่งนี้แสดงให้เห็นถึงหลักการ Least Privilege (สิทธิ์เท่าที่จำเป็น) ซึ่งช่วยเพิ่มความปลอดภัยให้กับฐานข้อมูลโดยป้องกันไม่ให้ผู้ใช้แก้ไขข้อมูลหรือทำคำสั่งนอกเหนือจากหน้าที่ที่ได้รับมอบหมาย

### 3. การใช้งานวิว (View Usage)

**คำแนะนำ:**
1.  รันคำสั่ง SQL สร้างวิวชื่อ `employee_public`
2.  ให้สิทธิ์ `SELECT` บนวิวนี้แก่ `hr_user`
3.  ในฐานะ `hr_user` รันคำสั่ง `SELECT * FROM employee_public;` (แคปภาพผลลัพธ์ที่ทำได้สำเร็จ)
4.  (ทางเลือก) ลอง Select คอลัมน์ที่มีความลับจากตารางหลักเพื่อแสดงให้เห็นว่าเข้าถึงไม่ได้ หรือแสดงให้เห็นว่าวิวโชว์แค่บางคอลัมน์

**[ใส่ภาพประกอบที่นี่]**

**สรุปผลการทดลอง (Reflection):**
ข้าพเจ้าได้สร้าง View ชื่อ `employee_public` ซึ่งเลือกแสดงเฉพาะข้อมูลทั่วไป (`id`, `name`, `position`, `department`) และซ่อนข้อมูลสำคัญอย่างเงินเดือน (`salary`) ไว้ เมื่อให้สิทธิ์ผู้ใช้เข้าถึงผ่าน View แทนการเข้าถึงตารางโดยตรง ทำให้เรียนรู้ว่า View ทำหน้าที่เป็นชั้นความปลอดภัย (Security Layer) และช่วยลดความซับซ้อนในการเขียน Query สำหรับผู้ใช้ทั่วไป โดยที่พวกเขาสามารถใช้งานข้อมูลได้โดยไม่ต้องรู้โครงสร้างตารางจริงหรือเข้าถึงข้อมูลที่เป็นความลับ

### 4. การสร้างดัชนี (Index Creation)

**คำแนะนำ:**
1.  รันคำสั่ง `CREATE INDEX` สำหรับคอลัมน์ `department` และแบบ Composite index
2.  รันคำสั่ง `\d employee` ใน psql terminal เพื่อดูรายละเอียดตาราง
3.  แคปภาพผลลัพธ์ที่แสดงรายชื่อ Indexes `idx_department` และ `idx_pos_date`

**[ใส่ภาพประกอบที่นี่]**

**สรุปผลการทดลอง (Reflection):**
ข้าพเจ้าได้สร้าง Index แบบปกติบนคอลัมน์ `department` และแบบ Composite Index บนคอลัมน์ `position` ร่วมกับ `hire_date` เพื่อเพิ่มประสิทธิภาพในการค้นหาข้อมูล จากคำสั่งตรวจสอบโครงสร้างตาราง (`\d employee`) พบว่า Index ถูกสร้างขึ้นเรียบร้อย การทำ Index มีประโยชน์อย่างมากในการลดเวลา Query ข้อมูลที่มีเงื่อนไข `WHERE` ตรงกับคอลัมน์ที่ทำดัชนีไว้ แม้ว่าจะต้องแลกมาด้วยพื้นที่จัดเก็บที่เพิ่มขึ้นเล็กน้อยและการเขียนข้อมูล (Insert/Update) ที่ช้าลงบ้างก็ตาม

### 5. การวิเคราะห์คิวรี่ (Query Analysis)

**คำแนะนำ:**
1.  **กรณีมี Index:** รันคำสั่ง `EXPLAIN ANALYZE SELECT * FROM employee WHERE department = 'IT';` (แคปภาพ) ให้สังเกตคำว่า "Index Scan" หรือ "Bitmap Heap Scan" ในผลลัพธ์
2.  **กรณีไม่มี Index:** รันคำสั่ง `EXPLAIN ANALYZE SELECT * FROM employee WHERE name = 'Bob';` (แคปภาพ) เนื่องจากคอลัมน์ name ไม่มี index ให้สังเกตคำว่า "Seq Scan" (Sequential Scan) ในผลลัพธ์
3.  เปรียบเทียบ "Execution Time" และประเภทของการ Scan ระหว่างสองกรณีนี้

**[ใส่ภาพประกอบที่นี่]**

**สรุปผลการทดลอง (Reflection):**
จากการใช้คำสั่ง `EXPLAIN ANALYZE` เพื่อเปรียบเทียบแผนการทำงานของ Query พบความแตกต่างอย่างชัดเจน ระหว่างการค้นหาด้วย `department` (ที่มี Index) ซึ่งระบบใช้การทำ "Index Scan" (หรือ Bitmap Scan) เพื่อเข้าถึงข้อมูลโดยตรง ทำให้ใช้เวลาน้อยกว่า เปรียบเทียบกับการค้นหาด้วย `name` (ที่ไม่มี Index) ซึ่งระบบต้องทำ "Seq Scan" หรืออ่านข้อมูลไล่เรียงไปทีละแถวทั้งตาราง การทดลองนี้แสดงให้เห็นว่า Index ช่วยลดปริมาณข้อมูลที่ระบบต้องอ่าน และเพิ่มความเร็วในการประมวลผลคำสั่ง SELECT ได้อย่างมาก โดยเฉพาะเมื่อข้อมูลมีขนาดใหญ่ขึ้น
